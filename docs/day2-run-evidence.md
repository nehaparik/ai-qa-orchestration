## Fault safety verification

- `--day2-fault` defaults to `None` (registered in
  `tests/day2/conftest.py`); confirmed by reading the registration and
  by every "baseline" run above using no flag and getting real
  enforcement.
- Confirmed by repo-wide search that nothing else references or sets
  this option: no CI workflow file exists, no `pytest.ini`/`tox.ini`,
  and `pyproject.toml`'s `[tool.pytest.ini_options]` has no `addopts`
  that could default it on.
- Each fault is scoped to only the test(s) that explicitly request its
  fixture (`ownership_fault`, `service_status_fault`) — not `autouse` —
  so running the rest of the suite, or running with an unrelated fault
  value, never activates it by accident (verified in Lessons 3 and 4).
- `monkeypatch` (pytest's built-in fixture) restores the real function
  automatically at the end of the one test that used it, pass or fail.
  No persistent data file and no authentication behaviour is ever
  touched by any fault.

## Report review (credentials, tokens, sensitive environment metadata)

`reports/day2/baseline.html`, `baseline.json`, `ownership-fault.html`,
and `ownership-fault.json` (generated by `pytest-html` /
`pytest-json-report`, per the README's "Generating a report" section)
were reviewed for anything unsuitable for Git:

- **No credentials, tokens, API keys, or passwords** were found in any
  of the four files.
- **No secrets** — this project has none; `X-Demo-Employee-ID` is a
  synthetic demo header, not a real credential, and `.env` does not
  exist on disk (only the tracked placeholder `.env.example`).
- **The self-contained HTML reports** embed no absolute file paths,
  hostnames, or usernames.
- **The JSON reports** (`pytest-json-report`'s own format) do embed the
  local absolute repository path (in their `"root"` field, and in the
  traceback file paths for the two fault-induced failures) — this is
  local-machine filesystem metadata, not a credential, but it is still
  local-environment information that shouldn't be shared verbatim.

**Action taken:** `reports/` is fully git-ignored (`.gitignore:9`,
confirmed with `git check-ignore -v`), so none of the four files reach
Git regardless of this review. This document and
`docs/day2-instructor-map.md` report every result using only relative,
sanitised paths (e.g. `tests/day2/test_03_ownership.py`) and never
reproduce raw report file contents — that is the "sanitised teaching
evidence" kept in the repo; the raw reports stay local-only, regenerated
fresh by whoever runs the commands in their own README-documented way.

## Limitations

- **Unsupported coverage** (not a gap, a real architectural limit of
  this Week 1 app): no write endpoints, no ticket-listing/collection
  endpoint, no query parameters or request bodies anywhere, no real
  authentication/authorization beyond the demo header, no rate
  limiting/pagination/versioning, and HTTP 405 on an existing route was
  deliberately left out as framework routing behaviour rather than a
  project-defined rule. Full list:
  [`docs/week01-api-case-matrix.md`](week01-api-case-matrix.md#documented-unsupported-coverage).
- **Pre-existing, unrelated to Day 2:** `pyproject.toml` has
  `requires-python = ">=3.11,<3.13"` commented out (present before this
  session; noted in `docs/day2-instructor-map.md`'s initial
  reconnaissance). An empty, untracked `practise-day1.py` also exists at
  the repo root — a scratch file, not a Day 2 deliverable.
- **One pre-existing doc fix made as part of this submission prep:**
  the README's macOS/Linux "Running the API locally" command previously
  said just `python` (a doc error, not a code bug); it now matches the
  Windows section's `uvicorn app.main:app --reload --port 8000`.
